# Knowledge System Blueprint

> Objective：把现有员工知识库、自动学习、长期记忆和制作上下文收口为一个适合一人漫剧团队的
> 知识中枢，在不推翻 JSON/PG 双模式的前提下降低重复、冲突和操作成本。

## 0. 执行约束

### 全程不变量

1. `master` 保持可部署；每个步骤使用 `codex/` 前缀短分支或当前规划分支上的独立提交。
2. 不迁移或删除用户现有 89 篇知识文档、长期记忆和制作卡片，迁移必须可回滚。
3. JSON 零依赖模式继续可用；PG/pgvector 是增强项，不成为本地启动硬依赖。
4. 向量、自动学习和长期记忆失败不能阻断 Agent 主调用，但降级状态必须可观察。
5. 功能代码变更同步 `docs/CHANGELOG.md`；架构/运行方式变化同步 README/架构文档。
6. 不接入 Letta、不建设真正内容知识图谱、不引入新基础设施。

### 完成定义

- 所有检索入口共享同一服务和回退语义；
- 所有在线入库入口都会调度索引并能清理旧向量；
- 会话长期记忆只处理新增消息范围；
- 前端提供单一“知识中心”入口，旧路由兼容；
- 有后端测试、前端类型检查/构建和一人工作室操作手册；
- 每个提交都能独立回退。

## 1. 依赖图与并行机会

```text
S1 架构契约与基线
 ├─► S2 兼容元数据、统一入库/检索 ─► S5 项目正典与上下文组装 ─► S6 评测与可观测
 ├─► S3 增量记忆 ────────────────────────────────► S6
 └─► S4a 知识中心静态入口 ─► S4b 状态与治理 UI ───────────────────► S6
```

- S2、S3、S4a 在 S1 后可并行，但 S2/S3 都会触及测试夹具，合并时应先 S2 后 S3。
- S4b 依赖 S2 的状态和索引任务契约；S4a 只能展示已有真实数据与规划标签。
- S5 依赖 S2 的作用域检索契约。
- S6 是发布门禁，依赖 S2、S3、S4b、S5。

## S1 — 固化知识边界与回归基线

**建议模型**：强模型。
**依赖**：无。
**回滚**：仅删除新增文档和测试清单，无运行时影响。

### 冷启动上下文

系统已经存在 `KnowledgeStore`、`KeywordRetriever`、`SemanticRetriever`、三层长期记忆、
文章学习、提示词采集和制作卡片。问题是同一项目事实散落在角色提示词、知识文档、记忆与卡片中。
本步骤只定义唯一事实源和未来契约，不迁数据。

### 任务

1. 新增 `docs/KNOWLEDGE_ARCHITECTURE.md`，明确词汇、唯一事实源、生命周期、检索和记忆准入。
2. 记录当前文档、记忆、知识源和主要入口基线。
3. 为后续步骤列出必须保持的现有 API 契约。
4. 在 README 文档导航增加知识体系入口。

### 验证

```powershell
rg "唯一事实源|统一检索|记忆准入" docs/KNOWLEDGE_ARCHITECTURE.md
git diff --check
```

### 退出条件

- 任一开发者能回答“角色 DNA、岗位 SOP、制作事实、用户偏好各存哪里”。
- 明确列出暂缓项，避免继续横向加系统。

## S2 — 建立兼容元数据并统一知识入库与检索入口

**建议模型**：强模型。
**依赖**：S1。
**回滚**：恢复各调用方原来的 `knowledge_store`/`knowledge_retriever` 调用；不改存量格式。

### 冷启动上下文

手工上传会触发向量化；文章学习和提示词采集直接调用 `KnowledgeStore.upload()`，导致索引行为不一致。
对话和搜索 API 走 `retrieve_knowledge()`，工作流节点和 Agent 工具只走关键词。

### 任务

1. 先以兼容默认值扩展 `spaceType/spaceKey/kind/status/authority/contentHash/indexStatus/revision`，旧数据不迁移也可读。
2. 为 JSON/PG 建立参数化存储契约：空间内哈希唯一、revision CAS、UTC、稳定排序、原子写/事务。
3. 新增 `knowledge_ingestion` 服务，封装上传、持久化任务、索引、删除和旧索引清理。
4. PG/队列模式使用 outbox；JSON 使用持久任务箱；启动时自动重放未完成任务并提供显式重试。
5. 索引携带 `jobId/generation`，完整构建后原子激活，再清理旧 generation；删除使用 tombstone。
6. 手工上传、文章学习、提示词采集改走统一入库服务。
7. 工作流知识节点与 `query_knowledge_base` 工具改走统一异步检索入口。
8. 约束 `topK`，空查询快速返回；根据“PG+队列 / PG 无队列 / JSON”定义 fail-open 与任务持久化矩阵。
9. 为 API、文章、采集替换、工作流/工具、进程崩溃、重复重放和 tombstone 补测试。
10. 更新 `docs/ARCHITECTURE.md`、`MODULE_INDEX`、`CHANGELOG`。

### 验证

```powershell
pytest -q tests/test_vector_store.py tests/test_registry_store.py
pytest -q
```

### 退出条件

- 在线产生知识文档的入口都调度相同索引逻辑。
- 删除/替换文档不会遗留旧向量。
- 相同 query 从 API、Agent 工具和工作流节点得到同一回退语义。
- JSON/PG 契约测试和“构建后崩溃、激活后崩溃、清理前崩溃”的恢复测试全部通过。

## S3 — 长期记忆改为增量准入

**建议模型**：强模型。
**依赖**：S1；可与 S2/S4a 并行。
**回滚**：保留旧 `extract_and_store(messages, ...)` 兼容入口，关闭增量调度即可恢复。

### 冷启动上下文

`run_invocation()` 在会话达到四条消息后，每次把完整历史交给记忆提取器。经验记忆不去重，
会产生重复 LLM 调用和记忆污染。会话模型已有可扩展 `metadata`，可保存处理游标。

### 任务

1. 为消息补充不可变 `messageId` 和单调 `sequence`；旧会话读取时一次性回填并持久化稳定值。
2. 新增 `extract_session_delta()`，以 `lastMemorySequence` watermark 只读取新增消息范围。
3. 用 `sessionId:startSequence:endSequence:extractorVersion` 生成幂等键；候选记忆按内容哈希 upsert。
4. PG 在事务中锁定会话并完成记忆 upsert + 游标 CAS；JSON 使用跨进程文件锁、临时文件与原子替换。
5. 无价值范围也推进游标；调用失败不推进。若记忆成功但游标写入失败，重试命中同一幂等键。
6. `run_invocation()` 和手动提取 API 改用增量入口；进程内 session 锁仅作为削峰，不承担正确性。
7. 增加重复调用、失败重试、多进程竞争、旧会话回填，以及“记忆已写/游标失败”恢复测试。

### 验证

```powershell
pytest -q tests/test_memory_extractor.py tests/test_long_term_memory_db.py tests/test_memory_db.py
pytest -q
```

### 退出条件

- 连续三轮对话时，第二、三次只处理各自新增消息。
- 失败不会丢失待提取范围，成功不会重复提取同一范围。
- JSON 与 PG 在同一并发测试向量下产生相同的 watermark 和记忆集合。

## S4a — 建立一人团队知识中心静态入口

**建议模型**：默认模型。
**依赖**：S1；可与 S2/S3 并行。
**回滚**：删除新路由和导航；旧页面、旧路由保持不变。

### 冷启动上下文

知识文档藏在员工弹窗；文章学习、提示词采集、记忆、知识图谱分散在高级菜单。
员工弹窗还显示后端不支持的 PDF，以及不存在的 `chunkCount/createdAt` 字段。

### 任务

1. 新增 `/knowledge` 知识中心聚合页，展示已有真实数据、快速入口和推荐操作顺序。
2. 默认导航增加“知识中心”；旧高级页面保留兼容路由。
3. “知识图谱”用户可见名称改为“能力关系图”。
4. 员工知识弹窗只承诺 `.txt/.md`，展示真实 `uploadedAt` 和文件大小。
5. 页面把未落地的项目正典、收件箱状态明确标记为“规划中”，不伪造计数或状态。
6. 更新 README 与 CHANGELOG。

### 验证


### 退出条件

- 日常用户从一个入口能到达知识上传、学习源、采集源和记忆管理。
- 不再出现虚假格式、字段和“内容知识图谱”暗示。

## S4b — 展示状态并收口低维护治理

**建议模型**：默认模型。
**依赖**：S2、S4a。
**回滚**：隐藏状态与批量治理区；静态知识中心和旧页面不受影响。

### 冷启动上下文

S2 提供真实元数据、持久任务和索引状态。在此之前 UI 不能可靠展示 pending/degraded/failed，
也不能承诺“已发布即可检索”。一人团队不能每天逐条审批普通参考资料。

### 任务

1. 展示待索引、降级、失败、待审核数量及最近失败原因，并提供重试入口。
2. 只让项目正典、高权威冲突和行为规则改写进入逐条确认；普通重复项自动合并。
3. 收件箱支持批量发布、批量驳回和按来源自动规则；设置积压上限与过期提醒。
4. 增加“本周知识维护”视图，目标每周不超过 30 分钟。
5. 记录每集知识相关人工操作次数，若高于改造前基线则阻止默认流程扩张。

### 验证

```powershell
pytest -q
Set-Location web
npm run build
```

### 退出条件

- 任一索引失败可见、可重试，且不会把 pending 显示成 indexed。
- 默认流程不要求逐条审批普通文档；待审积压有上限，单周维护可在 30 分钟内完成。

## S5 — 项目正典与统一上下文组装

**建议模型**：强模型。
**依赖**：S2。
**回滚**：迁移只允许新增字段和旁路写入。切换前保存 JSON 文档/索引/员工配置，或 PG 数据库/向量表/员工配置的
一致性快照；使用功能开关双读并切回旧链路，按逐文档迁移日志恢复。旧字段和正文只在后续独立清理版本删除。

### 冷启动上下文

项目正典当前主要通过员工角色提示词副本和制作卡片传播。生产生成会把当前范围内所有前置卡片
拼进 prompt，随后 `run_invocation()` 再注入员工知识和长期记忆。

### 任务

1. 基于 S2 元数据建立项目正典空间和员工/岗位访问引用，不复制正文。
2. 新增 `ContextAssembler`，按任务指令→项目正典→生产事实→岗位 SOP→记忆排序。
3. 统一设置总 Token/字符预算、每来源上限和内容哈希去重。
4. 生产生成改为检索相关前置卡片，保留 shot/episode 显式过滤。
5. 编写存量文档的加法式回填脚本，默认 dry-run；逐文档记录前后哈希、版本、结果和恢复动作。
6. JSON 与 PG 分别定义包含正文、元数据、激活 generation、向量、员工配置的一致性快照命令。
7. 开启 dual-read/shadow-write，比较新旧结果；未通过门禁时旧链路仍为权威。
8. 去除员工 `roleProfile` 中项目正典副本前完成恢复演练；删除动作留到后续独立、可撤销版本。

### 退出条件

- 项目正典只有一个已发布版本作为权威来源。
- Agent 输出可追溯本次使用的正典、生产卡片和方法文档。
- 相比旧链路，上下文 Token 下降且评测不退化。
- 随机抽取文档与角色配置完成一次快照恢复演练，恢复后正文、元数据和激活索引哈希一致。

## S6 — 检索评测、可观测与发布门禁

**建议模型**：强模型。
**依赖**：S2、S3、S4b、S5。
**回滚**：评测和指标为旁路，不影响运行时。

### 冷启动上下文

现有 evals 只有少量 Agent 输出案例，缺少“问题→应命中文档/正典”的检索评测。
向量失败主要依赖日志，用户看不到降级状态。

### 任务

1. 冻结至少 20 条确定性检索 golden cases 与改造前结果，覆盖角色时期、场景、风格、镜头规范和项目冲突。
2. 检索使用固定语料、固定配置与稳定 tie-break，记录 top1/top3、权威等级、Token 和重复字符占比。
3. 前端状态指标由 S4b 提供；本步骤补采集延迟、任务重放次数和索引 generation 指标。
4. 将知识相关变更的最小评测接入 CI；需要 LLM key 的部分单独标记。
5. 用 EP01/EP02 做人工对照，记录返工率、Token 与人工操作次数，并保存基线。

### 验证

```powershell
pytest -q
python -m evals.run_retrieval_evals
Set-Location web
npm run build
```

### 退出条件

- 项目正典类用例 top3 命中率为 100%，全部用例 top3 不低于 90%。
- 固定任务上下文重复字符占比不超过 5%，Token、返工率和人工操作次数不得高于冻结基线。
- 任一索引降级可从 UI/API 看见。
- 一人团队从概要到完整草稿的操作路径有实测记录。

## 2. 计划变更协议

- **拆分**：单步预计超过 500 行有效代码或同时改后端、迁移和大型页面时，拆成连续子步骤。
- **插入**：发现数据丢失、权限绕过或上下文错误时，在当前步骤前插入修复步骤并记录原因。
- **跳过**：只有目标已由现有代码满足且有测试证据时可跳过。
- **调整顺序**：必须保持依赖图；S4b/S5 不得提前于 S2。
- **放弃**：Letta、独立向量库、真实知识图谱等暂缓项只有出现可量化触发条件才重新立项。

## 3. 对抗性审阅清单

- 是否仍有在线入库入口绕过统一服务？
- 是否存在模型自产事实未经确认进入长期记忆？
- JSON 与 PG 是否保持同一行为？
- 失败回退是否会静默伪装成“已索引”？
- 删除/替换是否遗留向量或元数据？
- 是否错误地把能力配置、制作状态和内容知识混成一类？
- 是否为一人团队减少了入口和操作，而不是新增管理负担？
- 是否能逐提交回滚且不触碰现有用户数据？
