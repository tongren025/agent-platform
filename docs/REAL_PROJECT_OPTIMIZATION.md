# 真实项目跑通与问题驱动优化

本闭环不再以“卡片数量增加了”作为完成标准，而是持续回答三个问题：

1. 当前交付目标还差什么？
2. 哪个问题应该最先处理？
3. 修复后是否真的变好，并且可以回溯？

## 用户主线

1. 在 `/studio` 新建或选择项目，并明确本次目标：文字分镜、镜头图片或完整成片。
2. 导演页只给一条当前动作。规格质量门禁失败时，先显示“定向返工”，不会继续消耗图片或视频额度。
3. 在 `/production/:pid/matrix` 查看项目健康分、阻塞问题和每个镜头的链路缺口。
4. 文本规格问题可点击“定向返工”；系统显示本次验收条件，并允许补充必须保留的
   画风、台词或剧情约束，只替换对应阶段和镜头。
5. 没有失败原因、只是处于 `review` 的历史卡片必须由人打开确认，不会被当成失败
   自动重写。
6. 图片/视频问题不会后台自动消费额度，而是返回导演页，由用户选择模型并确认费用。
7. 每次自动修复记录修复前后健康分、生成/替换数量、剩余质量问题和失败原因。

## 诊断口径

诊断严格服从项目 `production_goal`：

- `storyboard`：创意素材、剧本、逐镜分镜。
- `images`：在文字分镜基础上增加画面提示和镜头图片。
- `final`：增加视频提示、镜头视频和当前版本成片。

每个生产槽位使用 `(episode, shot_number, stage)` 定位，读取最后写入的卡片，避免旧
返工版本遮住新版本。旧 GC 若没有逐镜卡，但在 `prompt_order`、`shot_count`、
`prompt_count` 或 `keyframe_count` 中声明了镜头数，会按聚合项目计算，不会误报
“没有生产单元”。

健康分按当前交付目标的价值加权，不按卡片数量平均：

| 目标 | 权重 |
|------|------|
| 文字分镜 | 素材 10、剧本 35、分镜 55 |
| 镜头图片 | 素材 5、剧本 15、分镜 20、画面提示 20、图片 40 |
| 完整成片 | 素材 5、剧本 10、分镜 15、画面提示 10、图片 20、视频提示 10、视频 20、成片 10 |

每个阶段按实际完成比例取得对应分数。这样大型项目即使有数百个镜头，缺少当前成片
仍会明确扣除 10 分，不会因为单个成片检查被大量镜头卡片稀释后显示 100 分。页面同时
展示“内容规格 / 模型提示 / 媒体资产 / 交付成片”的分数组成。

问题按“阻塞 → 提醒 → 进行中”、再按生产阶段排序。首要问题就是导演页和完整性检查页
的下一条动作。

定向返工提示由当前问题、静态门禁代码和阶段验收条件共同生成。例如分镜字段缺失会
要求逐项补齐可生产字段；负向语言、视觉噪点、失稳运动和超 6 秒片段分别使用对应的
修改规则。用户补充要求会作为独立约束加入，但不会扩大返工范围。

## 安全与恢复

- 自动修复一次只处理一个诊断问题。
- 同一项目同一时间只允许一个自动修复任务。
- 质量返工使用现有 `replace + shot_number` 定向替换，并在覆盖前建立项目版本。
- 缺失阶段使用 `append`，不删除其他镜头或其他阶段。
- 生图、生视频不自动执行，必须由用户选择模型。
- 默认记录到
  `data/production/<project_id>/optimization-runs.json`，只保留最近 100 次，不依赖
  PostgreSQL 或 Redis。
- 单机单用户使用进程内并发控制；未来多进程部署需要把控制器替换为共享实现。

## API

- `GET /api/v1/agentapp/director/projects/{project_id}/diagnostics`
  返回 `status / summary / nextActions / artifacts`、健康分、检查项、问题和下一动作。
- `POST /api/v1/agentapp/director/projects/{project_id}/optimize`
  请求 `issue_id`，只执行仍然存在且标记为 `autoFixable` 的问题。
- `GET /api/v1/agentapp/director/projects/{project_id}/optimization-runs`
  返回最近的修复记录。
- `GET /api/v1/agentapp/director/feedback`
  聚合全部 JSON 项目的高频问题、低健康项目、自动/人工处理数量，以及实际修复
  成功率和平均提分。

## 当前真实项目基线

2026-07-30 使用仓库内项目只读扫描：

| 项目 | 健康分 | 主要阻塞 |
|------|-------:|----------|
| 九陆纪元 · 九大陆灾变史诗 GC（完整 V3） | 70 | 14 个镜头尚无视频 |
| 九陆纪元 · GC 概念宣传片 | 20 | 33 项待确认、11 张退回图片、11 个视频 |
| 九陆纪元 · 第一季 | 58 | 143 个视频、83 张图片 |
| 九陆纪元 · 第二季 | 50 | 144 个视频、143 张图片 |
| 九陆纪元 · 第三季 | 50 | 144 张图片、144 个视频 |
| 铁心恋人 · 第一季 | 50 | 72 张图片、72 个视频 |

当前合计 1,001 个待处理问题：缺视频 515、缺图片 442、等待人工确认 33、图片审核
退回 11。集级剧本、G 级提示和子镜头级分镜归一后，当前真实项目没有仍需自动补写的
文本规格；1,001 项均需要人工确认或选择媒体模型。平均健康分为 50；目前没有真实
自动修复记录，因此成功率暂不显示，第一次实际操作后开始从
`optimization-runs.json` 累计。

高频榜按数量反映工作量，“建议下一步”则按生产依赖选择；因此当前不会因为缺视频
数量最多就直接推荐生成视频，而会先提示处理待确认内容，再进入图片和视频阶段。

这张表是优化起点，不是要求一次性全部自动补齐。优先顺序应是：

1. 先确认待审核内容和退回图片，避免把未通过素材继续放大。
2. 再生图片并完成审核。
3. 只对已通过图片的镜头生成视频。
4. 全部当前版本视频就绪后再合成成片。

## 回归验收

端到端 dry-run 从一段创意开始，连续经过：

```text
创建项目 → 诊断缺少生产单元 → 生成结构化剧本
→ 诊断缺少分镜 → 定向补齐
→ 诊断缺少画面提示 → 定向补齐
→ 到达“选择模型生成图片”的人工费用边界
```

该路径使用测试替身，不访问外部模型；每一步都要求问题 ID 消失、健康分提升并写入
优化历史。真实媒体阶段继续使用导演页现有的模型选择、价格确认、审核和成片合成流程。
